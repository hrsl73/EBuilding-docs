Monthly Collection Entry in Finance

At the start of each month, the system adds one credit entry per society to the Finance module, showing the money actually received in the previous month from all bill collections. Gateway payments count at the amount Easebuzz settles, after its charges.

1. Goal & Summary

Society admins use the Finance module (backend name: expense) to record credits and debits. Today every entry is added by hand, so the income from bill collections isn't there unless an admin types it in. The figure they would type is also wrong for online payments: Easebuzz keeps a fee and GST, so the society receives less than the bill amount.

🎯
Goal
Give the admin a clear, correct figure for how much income came into the society in a given month through bill collections, in the same place they track all other finances.

In one line

At the start of each month, the system adds one credit entry per society to Finance. The entry is dated the last day of the previous month and holds the money received from every payment completed in that month, with a breakdown by payment type.

Out of scope

  • Changing how bills are created, paid or approved.
  • Refund and chargeback handling. Not needed.
  • Separate entries per bill type. One combined entry for now; a split may come later.

2. How It Works Today

Finance module (expense)

  • Model expense.model.js: user_id (required, the admin who added it), purpose, amount, transaction_type (cash | cheque | online, required), type (credit | debit), society_id, media_ids, date_of_expense, cheque_number, is_active (soft delete).
  • Routes under /society/expense: POST /create-society-expense, GET /get-society-expenses/:society_id, PUT /delete-society-expense/:expense_id (soft delete), plus report summary and Excel/PDF exports. Entries can be added and deleted but not edited.
  • Create flow: checks the caller is an active society admin, saves the entry, writes an activity log (EXPENSE_CREATED), then notifies society members. Members are skipped when society.is_expense_management_enabled_for_member is off.
  • Totals: the listing adds up credits and debits into profit/loss. A system credit entry flows into these totals with no extra work.
⚠️
Gap
Nothing on an entry says it was created by the system or which month it covers, so today we can't tell system entries apart from manual ones or stop duplicates.

Payments (transaction)

  • module_type: maintenance, special_bill, member_charge, subscription, ai_subscription, vendor_credit.
  • transaction_type: cash, cheque, online (paid outside the app, receipt uploaded and approved by the admin), gateway (Easebuzz).
  • Completed statuses: success, approved.
  • approved_at is set when a payment becomes success/approved, by the gateway callback or by admin approval. Payments the admin records directly get it at creation.
  • maintenance_id is an array: one payment can cover several bills.

The Easebuzz object (payment_gateway_response)

The gateway callback handler in transaction.service.js stores these Easebuzz fields on every gateway payment:

Stored keyEasebuzz fieldMeaning
payment_amountamountWhat the member paid
service_feeservice_chargeEasebuzz fee
service_taxservice_taxGST on the fee
net_amount_debitnet_amount_debitAmount debited from the payer
settlement_amountsettlement_amountAmount settled to the society. This is the figure we count.

Easebuzz rates can differ by payment mode (UPI, card, netbanking), so we use these stored figures and never calculate the fee with a fixed percentage.

Existing reports

The Maintenance Collection Report groups paid bills by bill month and shows the full bill amount. The Transaction Report filters by payment date. This feature follows payment completion date, so its figure will match neither report's gross figure exactly.

3. Business Rules

#Rule
R1One system credit entry per society per month, created automatically.
R2The entry is dated the last day of the month it covers (IST).
R3A payment belongs to the month in which it was completed, not the month of the bill it pays.
R4All society bill collections count: maintenance, special bills, water charges, advance payments, place bookings and dues. See section 4.
R5Cash, cheque and manual online payments count at their full amount.
R6Gateway payments count at settlement_amount from the Easebuzz object on the payment, the amount actually received.
R7The entry carries a breakdown by payment type so it can be audited, and shows the total amount deducted by the gateway for the month.
R8Entries created by the monthly job or the past-months script are owned by the system, not by any admin. A re-logged entry is owned by the admin who re-logged it.
R9Months with no collections get no entry.
R10Admins can delete a system entry, and can log any past month again from the create form.
R11The monthly job only handles the month that just ended. Past months of the current financial year are added once by a separate one-time script, and admins are told about it with a pop-up.
R12Notifications follow the society's existing Finance visibility setting. Backfilled months send no notifications.
R13No new collection. An activity log is written whenever a system entry is added.
R14The feature is controlled by a global flag (super admin, admin console) and a society-level toggle in Feature Configuration that the society admin turns on or off.

4. What Gets Counted

We add up payments, not bills. One payment can cover several bills. Bills covered by an advance payment get marked paid without any new money coming in (include_in_advance_payment). Counting payments means each rupee is counted once, in the month it was received.

SourceStored asCounted?
Monthly maintenance billsmodule_type: maintenanceYes
Water chargesPart of the maintenance bill (water_unit, water_unit_price)Yes (covered by the bill payment)
Special billsmodule_type: special_billYes
Place bookings paid onlinemodule_type: special_bill, empty maintenance_idYes
Advance paymentsLinked from advancePayment.transaction_idYes, in the month the advance was paid
Dues / late chargesmodule_type: member_chargeYes
Society subscription, AI subscriptionsubscription, ai_subscriptionNo (paid to the platform)
Vendor walletvendor_creditNo (vendor money)

Which payments

  • Status success or approved.
  • approved_at falls inside the month, using IST month boundaries (dayjsIst().startOf("month") to endOf("month")). Payments with no approved_at are skipped and logged; this is rare.
  • Belongs to the society.

5. Amount Calculation

Payment typeGrossDeductionsNet (counted)
cashamountNoneamount
chequeamountNoneamount
online (manual)amountNoneamount
gatewaypayment_amountservice_fee + service_taxsettlement_amount

Entry amount = sum of the net figure across all counted payments.

Gateway charges shown on the entry

The entry also shows how much the gateway deducted in the month, so admins can see why the figure is lower than what members paid:

Gateway charges = gateway gross − gateway net (counted), summed across the month's gateway payments.

  • Calculated as gross minus net, not fee plus GST, so the three figures (gross, charges, received) always add up with no rounding gaps between fee, GST and settlement.
  • Cash, cheque and manual online payments have no charges.
🔍
Decided: settlement_amount
The net figure for a gateway payment is settlement_amount. Before build we still count successful gateway payments on dev with an empty settlement_amount. In the current code every successful gateway payment gets these fields from the Easebuzz webhook, so the count is expected to be zero. If older payments turn out to be missing them, that is handled in the past-months script, not in the monthly entry. If the job ever meets a payment with no settlement_amount, it writes a server log for developers; admins see nothing extra.

6. Monthly Job

Schedule

The job runs on the 1st of each month for the month that just ended. Running at 00:00 is risky: several jobs already run then, and payments completed in the last minutes of the month could be missed. The early-morning slots already in use (IST):

TimeExisting jobs
00:00Recharge plan expiry, due charges check, hourly support-chat SLA and vendor review lock, 4-hourly WhatsApp retry
00:05No-show guest expiry
01:00 / 01:30Analytics metrics / analytics buckets
02:00Vendor score, analytics retention, monthly society health snapshot (1st only)
03:00 / 03:30Vendor tag backfill / FCM orphan cleanup
04:00Vendor temp area cleanup, WhatsApp retry
04:30 (prod)Database export (heavy)
🕔
Proposed: 05:20 IST on the 1st ("0 20 5 1 * *"). Timing to be confirmed.
05:00–06:59 has no daily job. 05:20 runs after the database export and avoids the :00, :10, :15 and :30 marks used by recurring jobs.
📅
Scope: the month that just ended, nothing else
Each run handles only the previous month. It doesn't catch up on missed or earlier months, and nothing runs when a society turns the toggle on. Past months come only from the one-time script (section 7) or a manual re-log (section 8). This keeps the job simple and avoids surprise entries.

Flow

1
Check the global flag
If the feature is off platform-wide, log and stop.
2
Load societies with the Feature Configuration toggle on
Process them in batches so one large run doesn't load the server.
3
Skip if the month already has an entry
Any system entry for that society and month, including a deleted one, means skip. A deleted month only comes back through a manual re-log.
4
Add up the month's payments
Apply sections 4 and 5. Build the per-type breakdown and the list of payments counted.
5
Skip empty months
No payments, no entry.
6
Create the entry, log it, notify
Create the credit entry dated the last day of the month, write the activity log, and send notifications per the society setting.
7
Isolate failures
One society failing is logged and doesn't stop the others. The whole job sits in try/catch like every existing cron, since an unhandled rejection shuts the process down.

7. Past Months & Pop-up

Many societies use Finance for their audit report, so we can't silently add months of entries. We backfill once and tell admins clearly.

  • Range: the current Indian financial year (1 April to 31 March), up to the last completed month. If run in November 2026, that's April–October 2026. From then on the monthly job takes over.
  • How: a one-time script, separate from the monthly job, using the same calculation code. One entry per month with collections, for every eligible society: global flag on, society toggle on (on by default), and at least one month with collections to enter. The script itself is written later, when convenient.
  • Societies that turn the toggle on later get no automatic past months. The monthly job picks them up from the next month end, and the admin can add earlier months with re-log.
  • No notifications for backfilled entries.
  • Pop-up: after the script runs, society admins see a pop-up telling them that the collection entries were generated by the system, that they can review them in Finance (and delete any they don't want), and that if they don't want this feature they can turn it off in Feature Configuration. It shows until that admin opens the Finance module. Seen status is saved on the server per admin, so it doesn't come back on another device.
🛑
Production safety
The backfill writes to many societies at once. It runs on production only with explicit approval, after a dry run on dev, and the dry run's figures are checked first.

8. Delete & Re-log

  • Delete: admins delete a system entry the same way as any entry (soft delete, is_active: false).
  • Re-log: the create form gets an option to log the system entry for a chosen month. The backend calculates the figures with the same code as the monthly job. Nothing is entered by hand.
  • Re-logged entry: identical to a monthly-job entry (same amount, breakdown, transaction_ids, type and notifications). The only difference is ownership: user_id is the admin who re-logged it.

Re-log is refused when

  • The month isn't over yet.
  • The month already has an active system entry.
  • The month has no collections.
  • The feature is off for the society.

The form can list the months that can be re-logged (past months with collections and no active entry), so the admin doesn't have to guess.

10. Feature Flags

The feature reaches every society, behind two flags:

LevelWhereWho toggles
GlobalNew field in PlatformConfig (single config document, read through a short cache)Super admin, ebuilding-admin console
SocietyNew boolean on the society model, shown as a toggle in Feature Configuration → Expense Management, next to "Show Expenses to Members"Society admin

One helper evaluates both and returns { enabled, reason } (GLOBAL_DISABLED / SOCIETY_DISABLED), like evaluateStaffAttendanceModuleStatus. The monthly job, backfill script, re-log endpoint and pop-up all use it.

  • Global flag off: the toggle is hidden in Feature Configuration and nothing runs for any society.
  • Saving the toggle goes through the existing Feature Configuration save, so it gets the existing activity log (feature_config) and "Feature Configuration Updated" notification with no extra work.
  • Turning it on only makes the society eligible for the next month-end run. It doesn't create entries by itself.
💡
Default: society toggle on
Every society starts with the feature on. Entries land in audit-sensitive Finance data, so the release update and the pop-up both tell admins the entries are system-generated, that they should review them, and that they can turn the feature off in Feature Configuration.

11. Data Model Changes

expense (proposed additions)

FieldTypePurpose
sourceString enum: manual | system, default manualTells system entries apart. Existing rows read as manual.
periodString YYYY-MMThe month the system entry covers.
breakdownObjectPer payment type: count, gross, net. Gateway also has fee, GST and total charges (gross − net).
transaction_idsObjectId[] → TransactionEvery payment counted, so each figure can be traced and recalculated.
user_idChange: not required when source is systemEmpty for monthly-job and script entries (system ownership, same approach as the activity log). Set to the admin for re-logged entries.
transaction_typeChange: new dedicated value for system entries (name to be decided)One entry spans several payment types, so it gets its own type instead of cash/cheque/online. The breakdown carries the amount received per type, and filters use it (see Filtering by payment type).

Index: unique partial index on { society_id, source, period } where is_active: true and source: system. This blocks duplicates and still allows re-logging a deleted month.

Filtering by payment type

A system entry holds the total received through every payment type. When the admin filters Finance by payment type, the entry still shows, but only with the amount received through the selected type.

🧮
Example
October entry = ₹50,000, of which ₹20,000 came in cash. Filter Cash · Credit → the October entry is listed with ₹20,000. With no payment-type filter it shows the full ₹50,000.
  • Matching: a system entry matches a payment-type filter when its breakdown has money for at least one selected type. Entries with nothing in the selected types are hidden.
  • Amount shown: the sum of the breakdown's net amounts for the selected types. With the multi-select filter (e.g. Cash + Cheque), the selected portions are added together.
  • Totals: credit totals and profit/loss under a payment-type filter use the same partial amount, so the totals match the rows shown.
  • Reports and exports: the report summary's per-payment-method totals, and the Excel/PDF exports with a payment-type filter, split system entries by their breakdown the same way.
  • Gateway money: Finance has no "gateway" filter option. Proposed: the gateway portion counts under Online, together with manual online payments (to confirm).

Example breakdown (illustrative figures)

{
  "cash":    { "count": 12, "gross": 36000,  "net": 36000 },
  "cheque":  { "count": 3,  "gross": 9000,   "net": 9000 },
  "online":  { "count": 2,  "gross": 6000,   "net": 6000 },
  "gateway": { "count": 40, "gross": 120000, "service_fee": 240, "service_tax": 43.2,
               "charges": 283.2, "net": 119716.8 }
}
// amount = 36000 + 9000 + 6000 + 119716.8 = 170716.8

13. UI Changes

Society app (Finance)

  • System entries show a "System" label and a readable purpose, e.g. "Collections for October 2026".
  • The system entry shows the gateway charges on the entry itself, e.g. "Gateway collections ₹1,20,000 · Gateway charges −₹283.20 · Received ₹1,19,716.80".
  • Opening a system entry shows the breakdown by payment type, including the gateway fee and GST.
  • Delete works as for other entries.
  • Create form: an option to log the system entry for a past month, with a month picker limited to months that can be re-logged.
  • Pop-up after the past-months script: entries were generated by the system, review them, turn the feature off in Feature Configuration if not wanted. Shows until the admin opens Finance.
  • Under a payment-type filter, a system entry shows only the amount received through the selected types.
  • All new text in English, Hindi and Gujarati.

Society app (Feature Configuration)

  • New toggle in the Expense Management section, e.g. "Auto-add monthly collection entry", with a short description that the entry is added after each month ends.
  • Hidden when the global flag is off.

Admin console

  • Global toggle in Platform Config. No per-society toggle.

Bill settled from an existing advanceNot counted again. The advance was counted when it was paid.

Gateway payment missing fee fieldsNot expected in current code. If it happens, a server log is written for developers (open item 1).

Toggle turned off and back onMonths while it was off get no entry. They can be re-logged.
Global flag turned offToggle hidden, job and re-log stop for every society. Existing entries stay.
Two re-log requests at the same momentThe unique index lets only one succeed; the other gets a clear "already logged" error.
