1. Executive Summary & Core Objectives

Water meter billing is a vital recurring component of society maintenance bills. In society operations, maintenance bills often undergo updates, revisions, or deletions before final payments are collected. This PRD establishes a robust, resilient flow where water readings are entered directly within maintenance bill creation and preserved safely across bill edits and deletions.

🎯
Core Architecture Principles
  • Readings Only (No Physical Meter Entity): We focus strictly on recording flat-wise numerical readings (Previous & Current). No complex hardware meter entities.
  • Unified In-Flow Wizard: Water readings entry is an integrated step inside the Maintenance Bill creation wizard, not an isolated external screen.
  • Dedicated waterreadings Collection: Master flat records (floorunits) are never mutated or overwritten. Every reading belongs to its billing cycle.
  • Smart Reading Recovery: Deleting a maintenance bill cycle does not destroy recorded water readings. Re-generating the bill for that month detects existing readings and offers instant restoration.
  • Inline Table Editing: Admins can edit water readings directly in the maintenance review table with live recalculation of water charges and flat totals.
  • Open Units Only: Only occupied/open flats (owner, rent, shop) are eligible for water units. Closed flats (closed) are strictly excluded (₹0 charge).
  • Dedicated Clean APIs: Replaces legacy floorUnit mutations with dedicated /society/water-reading/* endpoints.

Wizard Steps Breakdown

Step 1: Duration Selection (/duration-maintenance-bill/:societyId)
Admin selects billing months (e.g., August 2026) and due date. On clicking "Next", the backend initializes an AdminMaintenance draft cycle and returns its admin_maintenance_id.
2
Step 2: Water Readings Entry (Integrated Wizard Step)
If the society has water meter pricing enabled (water_price_per_unit > 0), the wizard displays the Water Unit Entry step for this cycle:
  • Closed flats show as Closed and are disabled.
  • Open flats display their Previous Reading (automatically resolved from the latest valid cycle).
  • Admin enters Current Reading wing by wing. Consumed units are calculated live.
  • Admin clicks "Proceed to Review" → readings are saved to waterreadings linked to this maintenance_id.
3
Step 3: Review & Inline Editing (/create-maintenance-bill/:societyId/:id)
Admin reviews all flats in a summary table. In this table, the water reading column is an editable inline input. Modifying a reading instantly recalculates consumed units, water charges, and the flat's total bill live.
4
Step 4: Publish Bills
Admin clicks "Publish". The maintenance bills and water readings are finalized (is_draft: false). Push notifications and bill breakdowns are dispatched to residents.

3.3 Database Collection Schema: waterreadings

Every reading document is linked directly to the parent maintenance billing cycle (maintenance_id). We store a single, unambiguous consumed_unit field.

Field Name Type Required Description
_id ObjectId Yes Default MongoDB ObjectId.
society_id ObjectId (ref: "Society") Yes Reference to the Society.
wing_id ObjectId (ref: "Wing") Yes Reference to the Wing.
floor_unit_id ObjectId (ref: "floorUnit") Yes Reference to the Flat Unit.
maintenance_id ObjectId (ref: "AdminMaintenance") No Links reading directly to the maintenance billing cycle. Set to null if bill is deleted (detached state).
start_month Date Yes Billing cycle start month (e.g., 2026-08-01T00:00:00.000Z). Used for chronological querying.
end_month Date Yes Billing cycle end month.
previous_reading Number Yes Baseline reading from preceding cycle (e.g. 150).
current_reading Number Yes Current recorded reading for this cycle (e.g. 195).
consumed_unit Number Yes Chargeable units: max(minimum_water_unit, current_reading - previous_reading).
unit_price Number Yes Snapshot of society's rate per unit applied to this bill.
water_amount Number Yes Total water cost: consumed_unit * unit_price.
status String Yes Enum: ["draft", "billed", "detached"].
• draft: In review.
• billed: Published.
• detached: Parent bill was deleted; preserved for smart recovery.
is_deleted Boolean No (default: false) Soft-delete flag. Set to true only if admin explicitly discards detached readings.
created_by ObjectId (ref: "User") Yes Admin User ID who recorded/edited the reading.

Database Indexes

// 1. History query index (fast lookups of past readings for a flat)
waterReadingSchema.index({ floor_unit_id: 1, is_deleted: 1, start_month: -1 });

// 2. Billing cycle fetch index
waterReadingSchema.index({ maintenance_id: 1, is_deleted: 1 });

// 3. Uniqueness index per flat per active billing cycle
waterReadingSchema.index({ maintenance_id: 1, floor_unit_id: 1, is_deleted: 1 });

// 4. Month-matching lookup index for smart recovery
waterReadingSchema.index({ society_id: 1, start_month: 1, is_deleted: 1 });

4. Smart Reading Recovery on Bill Deletion & Recreation

In typical operations, an admin might delete a published maintenance bill to fix a due date, revise an additional expense, or correct general billing settings. They should not be forced to re-type 100+ water meter readings from scratch.

stateDiagram-v2 [*] --> Draft: 1. Readings entered for August Draft --> Billed: 2. Maintenance Bill Published Billed --> Detached: 3. Admin Deletes Maintenance Bill (Readings NOT destroyed!) state "Admin Re-creates Bill for August" as Recreate { Detached --> Detect: System detects saved August readings Detect --> PromptUser: Displays Recovery Prompt PromptUser --> Restore: Admin selects "Use Saved Readings" PromptUser --> Discard: Admin selects "Start Fresh" Restore --> Draft: Re-linked to new maintenance_id with pre-filled readings Discard --> [*]: Detached readings marked is_deleted true; pulls July baseline }

How It Works:

  1. When a Maintenance Bill is Deleted: AdminMaintenance and Maintenance bills are soft-deleted. The linked waterreadings are not deleted; their status is transitioned to: status = "detached", maintenance_id = null.
  2. When Creating a Bill for That Same Starting Month: The backend checks if any detached readings exist for that society and starting month: 
    const existingReadings = await WaterReading.find({
  society_id: societyId,
  start_month: targetStartMonth,
  status: "detached",
  is_deleted: false,
});
  3. User Prompt in UI: If matching detached readings are found, the UI displays a clean prompt:
    💡
    Existing Readings Found for August 2026
    We found 85 saved water readings for August 2026 from a previously deleted bill cycle.
  4. If "Use Saved Readings" is Selected: All flats instantly pre-fill with their previous and current readings. The readings are re-attached to the new billing cycle: maintenance_id = new_maintenance_id, status = "draft". If only flat 204 had a mistake, the admin simply edits flat 204 inline.
  5. If "Start Fresh" is Selected: The detached August readings are marked is_deleted: true, and the baseline previous readings are pulled from the preceding valid cycle (July).

Dynamic Recalculation Behavior

  • Changing Current Reading automatically updates: $$\text{consumed\_unit} = \max(\text{minimum\_water\_unit}, (\text{current\_reading} - \text{previous\_reading}))$$ $$\text{water\_amount} = \text{consumed\_unit} \times \text{unit\_price}$$ $$\text{total\_flat\_bill} = \text{maintenance\_amount} + \text{water\_amount} + \text{additional\_expenses}$$
  • Footer sums for total society water charges and total bill collection update immediately.

6. Business Rules & Calculation Logic

Rule 1: Flat Eligibility (Open Flats Only)

  • Open Flats (owner, rent, shop): Eligible for water readings and charges.
  • Closed Flats (closed): Strictly excluded. Billed water units = 0, water charge = ₹0. No water reading document is generated.

Rule 2: Minimum Water Units Floor

Enforced identically on both Frontend and Backend:

function calculateWaterUnits(previousReading, currentReading, minimumWaterUnit) {
  const prev = Number(previousReading) || 0;
  const curr = Number(currentReading) || 0;
  const actualUsage = Math.max(0, curr - prev);
  const minThreshold = Number(minimumWaterUnit) || 0;
  
  return Math.max(actualUsage, minThreshold);
}

7. Dedicated Water Readings API Specifications

We do not use floorUnit endpoints for water readings. Dedicated APIs under /society/water-reading manage the lifecycle cleanly:

Method Endpoint Permission Description
GET /society/water-reading/get-readings/:admin_maintenance_id MAINTENANCE_BILLS: VIEW Fetches all flat readings for a billing cycle (grouped by wing), including resolved baseline previous readings.
PUT /society/water-reading/bulk-update/:admin_maintenance_id MAINTENANCE_BILLS: CREATE Saves or updates flat water readings for the billing cycle (used in Step 2 and for inline table edits).
GET /society/water-reading/check-existing-readings/:society_id MAINTENANCE_BILLS: VIEW Checks if detached readings exist for a given start_month (query param) for smart recovery.
POST /society/water-reading/restore-detached-readings/:admin_maintenance_id MAINTENANCE_BILLS: CREATE Re-links detached readings to the newly initialized maintenance cycle when admin chooses "Use Saved Readings".
GET /society/water-reading/history/:floor_unit_id Access Token Returns the past 2–3 months of readings and consumption for a flat.

9. Backward Compatibility & Migration Plan

  1. First Cycle Baseline Fallback: For existing societies running this new flow for the first time, if no records exist in waterreadings, the system reads floorUnit.water_previous_unit as its baseline.
  2. Zero Master Overwrites: Once the first cycle is saved in waterreadings, all future previous readings are resolved exclusively from waterreadings. Master floorunits is never mutated again.
  3. Member Compatibility: Resident bill details and downloaded PDF receipts remain 100% backward compatible since Maintenance documents continue to hold the final snapshot amounts for display.
