1. System Overview & Architecture

In the current system, water meter billing is an add-on submodule built inside the maintenance billing cycle. Instead of modeling physical meters as independent entities with time-series readings, water meter readings are stored as simple scalar properties directly inside the flat unit record (floorunits) and snapshot copied into the individual maintenance bill record (maintenances).

Core Operating Principle
Each flat has only one active reading state. During bill generation, the admin enters the flat's latest reading. When the bill cycle is published, that latest reading overwrites the previous reading, and the latest reading is cleared.

6. How Many Months of Old Units Are Stored?

⚠️
Critical Insight: Zero History on Floor Units
The master flat record (FloorUnit) maintains no monthly history whatsoever. It is strictly a current-state pointer.
Storage Layer Retention Depth Structure Queryable As Time Series?
floorunits (Master Flat Record) 1 Billing Cycle Only water_previous_unit and temporary water_latest_unit. No. No dates, no timestamps, no monthly fields.
old_water_previous_unit (Inside floorunits) Event-based only Array of raw numbers ([120, 240]) appended only when manual meter reset is invoked. No. Untimestamped, unindexed, never read by frontend.
maintenances (Billing Cycle Records) Indefinite (All Past Bills) Each document contains water_previous_unit, water_latest_unit, water_unit, and cycle dates. Partially. Can only be reconstructed by aggregating the entire maintenance bills collection. If a month had no bill created, no reading exists.

7. Critical Limitations, Bottlenecks & Flaws (The Cons)

The 10 major architectural, data consistency, and user experience flaws in the current implementation:

1
Destructive State Overwrite
Critical Integrity Risk
When a bill is published, water_latest_unit is wiped to null, and water_previous_unit is overwritten with the latest reading. If the admin notices a typo right after publishing, the original baseline reading is permanently destroyed from floorunits.
maintenance.service.js:L341: water_previous_unit: latestFromPayload, water_latest_unit: null
2
Premature Master Mutation
Critical Integrity Risk
Entering readings immediately mutates the master floorunits document before a bill cycle is even confirmed. If the admin abandons the flow halfway, unbilled dirty readings remain permanently stored on the flat.
create-water-bill.tsx:L246: Directly calls PUT /society/floor-unit/edit-floor-units
3
No Physical Meter Entity
Architecture Flaw
Meters are equated directly to flats (Flat ≡ Meter). The system cannot handle meter serial numbers, meter replacements, installation dates, or flats with multiple meters (e.g. domestic vs flushing lines, commercial units).
No Meter or WaterMeter schema exists in the entire backend.
4
Calculation Inconsistency
Financial Discrepancy
The backend draft creation calculates water_unit = Math.max(latest - previous, 0) and completely ignores minimum_water_unit. Only the frontend applies the minimum. If a bill is generated via automated cron or API, the minimum threshold is bypassed!
Backend: maintenance.service.js:L137 vs Frontend: create-edit-regular-bill.tsx:L52
5
Opaque & Untracked Reset
Audit Blindspot
The "Reset Water Meter" function pushes the previous reading into an untimestamped array (old_water_previous_unit). It stores no record of who reset it, when, why, or what meter it was.
floorUnit.dao.js:L1502: $concatArrays: ["$old_water_previous_unit", ["$water_previous_unit"]]
6
Read-Only Final Bill Screen
UX Bottleneck
On the final bill review screen (/create-maintenance-bill), water meter readings are completely read-only. If an admin spots an erroneous reading on Flat 402, they cannot fix it inline; they must discard the entire bill and start over.
create-edit-regular-bill.tsx:L1633-1643: Static label rendering only.
7
No Photo Proof or Verification
Dispute Risk
Staff or guards entering meter readings cannot upload a photo of the physical meter dial. When residents contest high water charges, society admins have zero visual proof or audit evidence.
No image upload or media reference exists in water meter endpoints.
8
Rollover & Negative Rejection
Operational Blocker
The only validation is latest >= previous. When a mechanical meter reaches its maximum (e.g. 99,999) and rolls over to 00,005, the UI treats it as a negative reading error and blocks bill generation.
create-water-bill.tsx:L99: setNegative(prev => ({ ...prev, [floorId]: prevVal > numericVal }))
9
No Anomaly / Spike Warning
Typo Vulnerability
There is no historical baseline check. If a resident whose typical consumption is 40 units has 4,000 units entered due to a keyboard typo or severe water leak, the system calculates a massive bill with zero warning or confirmation prompt.
Zero outlier detection or standard-deviation checks in backend or frontend.
10
Fragmented 4-Step Navigation
Friction & Drop-off
Admin workflow is split across four distinct URL routes (/water-meter-reading → /water-create-bill → /duration-maintenance-bill → /create-maintenance-bill). Navigating away leaves partially saved wing states.
State passed through URL params and React Router navigation state.

8. Key Recommendations for the New Flow (PRD Input)

🚀
Foundation for the New PRD
The new flow should decouple meter management from maintenance billing while providing a unified, auditable, and resilient reading lifecycle.
Area Current State Proposed PRD Solution
Data Entity Flat fields on FloorUnit Dedicated WaterMeter model (meter number, type, installation date, flat link, status).
Readings Model Scalar fields overwritten on publish Dedicated WaterMeterReading time-series collection (reading value, reading date, photo evidence URL, recorded_by, bill_cycle_id).
Photo Proof None Optional/mandatory meter dial photo upload via camera/gallery in mobile and web.
Calculation Mismatched between frontend & backend Centralized calculation service applying tiered tariffs, minimum threshold, and rollover math.
Inline Editing Read-only during bill review Allow inline correction of meter readings directly on the draft maintenance bill review screen.
Anomaly Detection None Flag readings that deviate >200% from previous 3-month average with an "Unusual Spike" confirmation modal.
